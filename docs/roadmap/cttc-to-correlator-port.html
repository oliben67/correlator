00

Purpose

correlator is a from-scratch rewrite of cttc onto a new stack, with three structural changes beyond a technology swap:

  1. Sump (renamed Gateway) becomes a properly containerized, pluggable-transport service instead of a fixed Docker-container-over-HTTP-with-SSH-fallback design.
  2. Data streams (renamed Docker host) become a plugin-sourced concept — Docker-over-SSH is the first plugin, not the only possible one.
  3. Sumps can beget Sumps. A host reachable as a data stream can be promoted to a first-class, independently-connectable Sump of its own — a real mesh, not just today's gateway peer-discovery scaffolding.

Everything else — the correlation UX, the recording/track/snapshot model, the plugin-hostile lessons cttc already learned the hard way — is preserved and built on, not reinvented. Later sections cite the exact cttc/log-sump mechanisms each new piece replaces or extends, so the "why" stays traceable.

02

What must not regress

cttc's actual product value is the shared-timeline correlation UX: click a log line → the chart recenters/highlights on that timestamp (± a few seconds); click a point on a chart → the log panel jumps to the corresponding lines. This is implemented today via one shared, clickable timeline over CPU/MEM/NET charts, one event-density lane per log source, and virtual-scrolled log panels (app/renderer/app.js, index.html).

Every phase below is sequenced so this UX is working end-to-end as early as possible (Phase 5), and nothing after it is allowed to degrade it.

03

Current state of cttc (as surveyed)

3.1 Client

Electron 43 app, not a website today. Renderer is mostly hand-rolled vanilla JS/HTML/CSS (app.js, dependency-free canvas charting + virtual-scrolled log panels) with a partial, incremental TypeScript module carve-out (renderer/src/modules/{docker-host,gateway,events,preferences,redis-cli,status-bar}/) using jotai + preact in a few spots — most state is still module-level globals and localStorage, not a full component tree. Build: esbuild, TypeScript for type-checking only, electron-builder → NSIS/DMG/AppImage.

3.2 Gateway = Sump's predecessor

A Docker container running log-sump (generic, CTTC-agnostic — daemon registry, Redis-Streams record store, query layer, Transport ABC, gateway/API auth, mesh routes) extended by log-sump-extended (a thin FastAPI-router shim, create_app(extra_routers=[router]), reproducing cttc's original wire protocol so the legacy renderer keeps working unmodified). Four s6-supervised processes per container: log-listener, fluentd, redis (embedded), log-server. Three connection modes client-side: local, remote, remote-tunnel (fallback only). Auth: shared bearer token, X-CTTC-Token.

3.3 Docker-host connectivity → data-stream territory

log_sump.common.transport.Transport ABC, two implementations: LocalTransport (local docker CLI subprocess) and SSHTransport (paramiko, not the system ssh binary; sudo prepended remotely). Once connected: container listing, log streaming (docker logs -f --timestamps), stats polling. This Transport abstraction is the single best piece of prior art for the new data-stream plugin interface — it already anticipates non-Docker transports in its own docstring, it's just never had a second implementation.

3.4 Recording / snapshot / capture mechanism → recording/track/snapshot

Built on log_sump.common.sample_archive.write_archive. Produces .cttc-record/.cttc-metric binary archives today. This is a working mechanism to rename and reshape, not to build from zero.

3.5 Mesh / ownership scaffolding → prior art

gateway.py + gateway_mesh.py: /ping, /gateways/sync (peer discovery), /gateway/ownership/claim|rotate (signature-based, using an owner's SSH public key). Real, but currently single-tenant in spirit — no per-user data-stream visibility model (see §7.3).

3.6 Plugin history read before designing

cttc already tried and abandoned a runtime, directory-scanned, dynamically-imported plugin loader (log_sump.server.plugins, driven by Settings.plugins.directory). It was removed in favor of the current compile-time extra_routers composition specifically because of empty/missing-plugin-directory-at-deploy-time bugs and state-leak edge cases. The new Sump/data-stream plugin system (§5.4, §6.3) must have an answer for those two failure modes, not just re-invent the directory scanner with different naming.

3.7 Testing & CI

Client: Node built-in test runner (17 files) + one Electron E2E spec. Server: pytest + pytest-asyncio + fakeredis (46 files total). No automated test-on-push CI anywhere — the only GitHub Actions workflow in the whole tree is a manual-dispatch image-push job. Fixing this is in scope for Phase 0, not a someday item.

4.1 Bundler: esbuild retained

Originally scoped as a swap to Webpack + Babel, for wider plugin ecosystem and more conventional Electron+React+TS starter-template precedent. Reconsidered and reversed: cttc already proves esbuild works well for this exact app shape (fast rebuilds, native TS/JSX support, simple config), and the Webpack swap was a speed-for-ecosystem trade-off rather than a hard requirement — not worth paying for without a concrete need for a Webpack-only loader/plugin. Phase 4's app shell scaffold builds on cttc's existing esbuild setup (build/build-renderer.js) rather than replacing it; Babel is dropped along with it.

4.2 Fluentd → Fluent Bit

cttc's Fluentd config + custom Ruby output plugin is vendored wholesale from log-sump. Fluent Bit does not run Ruby plugins — this is a genuine reimplementation of the log-forwarding hop, most naturally as a Fluent Bit output plugin, or by having Fluent Bit's built-in Redis output write directly in the shape ingest.consumer already expects. Needs its own spike (Phase 1) before committing to one approach.

4.3 OpenTelemetry

Confirmed absent from cttc, log-sump, and log-sump-extended entirely. Treat as new infrastructure: instrument the Sump server (traces across transport → ingest → query, metrics for stream depth/consumer lag) from Phase 1 onward so it's load-bearing from day one rather than retrofitted.

05

Sump renamed Gateway

5.1 Provisioning flow

On correlator start:

  1. Detect local Docker (docker info or daemon socket probe).
  2. Docker present locally → install/run the Sump container locally (mirrors ensureLocalContainer()'s logic).
  3. Docker absent locally → prompt for SSH credentials to a remote host, verify Docker, provision the Sump there (mirrors ensureRemoteContainer() — SSH used for one-time provisioning only; ongoing traffic stays HTTP).
  4. Either way, the provisioned Sump is registered into the correlator instance catalog (§5.2).

5.2 correlator instance catalog

Lives in .correlator/. Structurally JSON documents, SQLite-backed — not a flat gateways.json-style file. JSON keeps the record shape close to what the app already reasons about; SQLite gives queryability and durability the flat file never had (concurrent-write safety, indexed lookups, audit history, last-seen timestamps).

sumps(id, name, connection_type, host, port, catalog_json, created_at, last_seen_at)
data_streams(id, sump_id, kind, source_ref, catalog_json, owner_user_id, is_private, created_at)
secondary_sump_links(child_sump_id, parent_sump_id, promoted_from_data_stream_id, created_at)
recordings(id, data_stream_id, sump_id, file_path, catalog_json, created_at)
tracks(id, recording_id, data_stream_id, sump_id, file_path, catalog_json, created_at)

catalog_json columns hold the full JSON document (so the JSON shape stays authoritative and human-inspectable); SQLite columns are the queryable projection over it.

Provenance: every recording and track keeps a foreign-key link back to the data stream (and transitively the sump) it was captured from — so "everything created via [sump, data stream]" is a plain indexed query, independent of which project (§8.3) a track/recording is later organized into.

Catalog manipulation UI: the sumps/data-streams management UI operates directly on the catalog_json documents — a JSON view is the primary manipulation surface, not a bespoke per-field form schema (see §9.3).

5.3 Auth model

One scheme, reused twice. Whatever token/credential mechanism correlator uses client → Sump is the same mechanism a Sump uses when talking to a secondary Sump it spawned (§7) — simplifying on cttc's single shared X-CTTC-Token model, no separate mesh-auth protocol needed.

Open question: today's token is shared per-gateway, not per-user; §7.3 depends on per-user identity existing somewhere — either the correlator↔Sump scheme already carries it, or it needs to grow one before Phase 8.

5.4 Sump plugin architecture modeled on pytest/pluggy

Explicit direction: get this as close as possible to how pytest plugins work. pytest's own plugin system (pluggy) independently solves both of §3.6's failure modes (empty/missing plugin directory, state-leak edge cases) while hitting the actual goal: install any properly-packaged library into the Sump's container image and have it integrate with zero code changes to the Sump itself.

Discovery — entry points, not a scanned directory. A plugin is an ordinary installed Python package declaring itself under a dedicated entry-point group (e.g. [project.entry-points."sump.plugins"], exactly like a pytest plugin declares itself under pytest11). At startup the Sump resolves that group via importlib.metadata.entry_points(group="sump.plugins") — a lookup over installed package metadata, not a filesystem scan. There is no "directory that might be empty or missing at deploy time" — a plugin either exists as a real, versioned dependency in the image, or it doesn't. pip install correlator-sump-plugin-ssh and it's discovered automatically, the same way pip install pytest-xdist just works.

Default-on, explicit opt-out — matches pytest's own default (every installed plugin auto-loads), a Sump-level equivalent of -p no:cacheprovider/PYTEST_DISABLE_PLUGIN_AUTOLOAD rather than an activation allowlist.

Hook specs, not one extra_routers list. Today's composition seam becomes an implementation detail the plugin manager drives internally — one hookspec among several a plugin implements whichever subset of:

HookspecPurpose
sump_plugin_info()Name/version/capability manifest.
register_transport(manager)Sump-level transport plugin; registers a TransportPlugin extending Transport's run/stream_lines/run_shell.
register_data_source(manager)Data-stream plugin (§6.3); list sources, stream logs, poll stats.
contribute_routes(app)Optional custom API endpoints — where today's extra_routers seam lives now, generalized.
on_health_check()Drives the sleep-mode mechanism below.

This unifies §5.4 and §6.3 into one plugin system. A Sump transport plugin and a data-stream plugin are the same PluginManager, the same entry-point group — they differ only in which hookspecs they implement. The SSH plugin is expected to implement both register_transport and register_data_source from one package.

Graceful degradation: sleep, don't crash. on_health_check() lets the plugin manager notice a plugin has become unavailable. When that happens, the functionality that specific plugin backs — not the whole Sump — transitions into a sleep-like/idle state: it stops polling/streaming, stops consuming resources, but stays registered in the catalog (§5.2) and resumes on its own once the health check passes again. Scoping call flagged in §12: read as per-plugin, not whole-process — correct if the intent was the entire Sump going idle.

First plugin: SSH (direct port of SSHTransport/paramiko, implementing both register_transport and register_data_source).

A High-severity bug reaching the app layer from an implicit-state bug two layers down is exactly the failure mode a real state machine is meant to make structurally harder to reintroduce. (BUG-0104 — log-sump's own container appearing in its own docker-host listing — is the historical bug §6.1's self-filter-by-default design already exists to prevent: direct validation that decision is grounded, not speculative.)

Translating "rock solid" into concrete practice for Sump-related work only:

1. One explicit Sump lifecycle state machine, not scattered flags.

provisioning→active⇄unreachable→retired
data-stream / plugin level: active⇄sleeping

The data-stream-level pair is precisely §5.4's on_health_check() mechanism, now framed as one state model spanning both levels rather than an ad-hoc per-feature flag. Implicit, duplicated, or UI-vs-backend-desynced state is the common root cause behind the daemon-registry (BUG-0035/0036/0060) and stuck-daemon (BUG-0109/0112) bugs above — a single authoritative state machine, with the UI as a pure read of it, structurally closes that class of bug rather than relying on catching each instance after the fact.

2. Mine cttc's own bug history into a regression corpus before/during Phase 2. The 19 bugs above are a ready-made checklist: each becomes a named regression test against the new Sump code before Phase 2 is considered done.

3. State-transition test coverage, not just feature coverage (§10). Every edge in the state machine above gets its own test — this is what actually catches "stuck in a weird state" bugs like BUG-0112, which feature-level happy-path tests reliably miss.

4. Post-Phase-2 stability gate. Once the state machine and catalog schema (§5.2) ship, treat them as a stable contract: further changes go through a REQ-NNNN with an explicit migration note, not an ad-hoc patch — the discipline that was missing when the same pill got reworked three times in two days.

5. Smaller UI surface, by construction. §9.5's sidebar consolidation already reduces the number of places Sump-related state can be shown inconsistently, compared to cttc's two-separate-sections-plus-status-pills design — a stability property of that decision, not just a UX simplification.

06

Data streams renamed Docker host

6.1 Self-host detection

Once connected to a Sump, correlator asks whether its own host is a Docker host. If so, its containers are offered as data-stream candidates — with the Sump's own container filtered out of the list by default, selectable manually for users who explicitly want to watch the Sump watching itself.

6.2 Remote host via SSH

User supplies another host the Sump can reach over SSH; the same container listing/log-streaming/stats-polling mechanics apply — reusing SSHTransport's behavior, generalized under the new plugin interface (§6.3).

6.3 Data-stream plugin interface

Realized through the same pytest/pluggy-style plugin manager as §5.4 — a data-stream plugin is just a package implementing the register_data_source hookspec, not a second plugin system. Must be genuinely source-agnostic ("any data for logs and stats is welcomed") — no assumption of Docker or even containers, only "a source that can be listed, and that emits logs and/or stats."

6.4 logstream plugin open item

The spec: connect to "a logstream server running either as a container (or not)", "leverage the existing configuration but output it to stdout/stderr", with support for "any output type supported by logstream."

The survey done for this roadmap could not confirm what output-type options actually exist — log-sump-extended is only a thin compat shim with zero output-sink abstraction of its own. The real "logstream server" is almost certainly log-sump itself (pulled in as a pinned dependency, not checked out anywhere in this workspace). Action item before Phase 7: survey log-sump directly.

Tentative shape either way: a lightweight process that takes log-sump's own daemon/stream config and taps its output onto stdout/stderr in a defined schema the Sump's ingestion can consume generically — but not locked in until the upstream survey happens.

6.5 kibana plugin

Confirmed in-scope-but-later. The only firm requirement so far: §6.3's plugin interface must not preclude it — Kibana as a source means "logs and stats from an Elasticsearch-backed system," a different shape from "logs and stats from a container/host." Treat as a design constraint on §6.3, not a Phase-N deliverable yet.

07

Secondary Sumps mesh / federation

7.1 Promotion flow

A host currently reachable as a data stream (§6) can be promoted: install a Sump container there too — same provisioning mechanics as §5.1, SSH-initiated from the parent Sump instead of from correlator directly.

7.2 Independence + reachability

The resulting secondary Sump's data stays reachable from the parent, but the secondary Sump is fully first-class afterward — any correlator instance can connect to it directly, exactly as it would a primary Sump. Build this on cttc's existing gateway-mesh prior art (/gateways/sync, ownership claim/rotate) rather than designing federation semantics from scratch.

7.3 Per-user data-stream catalog + privacy open question

New requirement beyond what cttc's mesh code does today: the Sump maintains its own catalog of the data streams created through it, per user, with a per-data-stream privacy flag a user can set to keep a stream out of other users' view.

cttc's current auth is one shared token per gateway, not per-user identity. This needs a decision before Phase 8: either §5.3's shared auth scheme already carries a distinguishable per-user identity, or a lightweight identity layer needs to be added to the Sump. Track as the single biggest open question in this roadmap (§12).

08

Data model

8.1 Containment rules as specified

  • A sump contains one or more data streams, and/or secondary sumps.
  • A recording (*.recording) contains one or more tracks (*.track).
  • A project (*.correlator) contains tracks, recordings, and their text/JSON exports (snapshots), organized however the user wants, by reference, never duplicated.
  • Independently of project membership, every recording/track retains a provenance link back to its data stream/sump, tracked in the catalog's SQLite store (§5.2).

8.2 File formats

*.recording and *.track are the renamed continuation of cttc's existing .cttc-record/.cttc-metric archives — same underlying mechanism, new extensions. Snapshots remain plain .json/text exports with no dedicated binary format.

8.3 Projects *.correlator

Modeled on VS Code's .code-workspace: a JSON file referencing recordings/tracks/exports by path plus a virtual-folder tree for logical grouping, independent of where the referenced files physically live. Default project always exists at a fixed location inside .correlator/ and never relocates; "Save As" creates a separate, independently-managed file elsewhere.

8.4 File-association / open-on-double-click

*.track, *.recording, and *.correlator files should open in correlator when double-clicked from the OS — electron-builder's fileAssociations config, plus the corresponding open-file/argv handling in the Electron main process.

10

Testing & CI strategy

  • App: Vitest, replacing the Node built-in test runner; keep an Electron E2E harness equivalent to run-e2e.sh's approach.
  • Server: pytest + pytest-asyncio + fakeredis, continuing log-sump's own pattern; add OpenTelemetry-aware integration tests once instrumentation lands (Phase 1).
  • CI: cttc has none beyond a manual Docker-push workflow. Standing up automated test-on-push CI for both app and server is explicit Phase 0 work — the port is the right moment to fix this, not a later cleanup pass.
  • Sump lifecycle: state-transition coverage, held to a higher bar than feature coverage elsewhere (§5.5). Every edge of the provisioning → active ⇄ unreachable → retired / active ⇄ sleeping state machine gets its own test, plus a named regression test per historical cttc Gateway/Docker-host/daemon bug — the one area of the port explicitly exempted from "test what the feature needs" in favor of "test the failure modes that already happened once."

12

Risks & open questions

  1. Per-user identity for Sump auth (§5.3, §7.3) — blocking for Phase 8, worth resolving as early as Phase 2 so the catalog schema doesn't need a breaking migration later.
  2. log-sump upstream survey (§6.4) — blocking for Phase 7 design; should happen well before Phase 7 starts.
  3. Fluentd → Fluent Bit feasibility (§4.2) — needs a short spike in Phase 1 before committing to one approach.
  4. Embedded vs. shared Redis — cttc bundles Redis in-container; worth an explicit Phase 1 decision, relevant once secondary Sumps and multi-user catalogs exist.
  5. Sleep-mode scope (§5.4) — read as "the functionality the failed plugin backs goes idle," not "the whole Sump process sleeps." Confirm before Phase 1 implements on_health_check() — the blast radius differs a lot between the two readings.
  6. Kibana plugin shape — deliberately undecided; tracked only as a constraint on the Phase 3/6.3 plugin interface.
